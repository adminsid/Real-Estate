# ADR 018: Separate listing synchronization from media delivery

Accepted for private-preview canary, November 13, 2026. Supersedes the shared lease and cron-only gallery scheduling in ADRs 016–017. Public release remains gated.

The primary traversal remains sequential. It requests unexpanded Property pages of 100 rows, retains the reviewed scalar field inventory, and atomically commits facts, tombstones, component versions, work records and the exact cursor. Calendar-minute due checks avoid completion-time jitter skipping a poll. Primary leases never include photo transfers or geocoding.

Core and complete manifest versions are independent. An unrequested expansion cannot erase retained photos. A newer core version hides an unvalidated old manifest until a complete, current hydration validates it; tied versions can fill missing projections. Stale jobs cannot defeat newer facts, permissions or tombstones. The read path checks current manifest eligibility before images, derivatives and conditional responses.

D1 job rows form the transactional outbox. Gallery, cover and local-variant queues carry identifiers only. Independent claims, retries, completion and consumer demand are fenced. Publication reserves capacity per class; accepted queue messages are not republished every two minutes while legitimately queued. Claimed work becomes recoverable after its claim expires. Failed queue delivery becomes an operator-visible dead letter. Deferred budget/cooldown work does not consume failure retries.

One private Durable Object per subscription dispatches all MLS REST, media, redirect and operator-check traffic. It consumes each bounded response before another upstream request starts, prioritizes due facts, and shares idle slots between galleries and covers. Admission records a durable uncertain intent and atomically reserves quota before network I/O; pacing waits are followed by fresh claim, permission and backoff predicates. Unknown outcomes retain byte reservations. This is a coordinator for upstream work, not a consumer request proxy.

Existing conservative ceilings remain: 550 ms between actual starts, 6,000/hour and 35,000/day requests, 3 GB/hour and 50 GB/day, with overlapping accounting buckets. Optional work cannot consume core reserves of 600/hour and 4,000/day requests, 300 MB/hour and 4 GB/day. Media transfers are serialized pending provider clarification. Parent media URL-regeneration cooldowns remain intact; no assumption of independent CDN quotas or an approved bulk-import exception is introduced.

Private R2 originals survive. Exact-revision retained originals with validated raster metadata recover interrupted D1 completion without another source transfer. Local jobs prepare fixed 480/1080-pixel covers and demand-driven display sizes, reusing persistent derivatives. Full composition and watermarks remain visible. Images activation was completed by the owner. The app ceiling is 100,000 preparation attempts/month; at published pricing that bounds this application's transformation usage around $50 before other services, shared usage and tax. It is not an account-wide billing cap.

Search responses return card fields, one cover and a ready-photo count, rather than whole gallery manifests and descriptions. Full listing details remain local. The viewer displays a small prepared preview before upgrading, and keeps explicit original-quality access. Preview starts with the old read fallback during warmup; `PREPARED_MEDIA_ONLY` is enabled only after coverage review. The prepared public configuration has no Images or MLS credential binding and uses queue producers for demand.

Cutover first fences and drains the old writer, then applies the additive migration and deploys the new Worker. An explicit D1 mode selects `legacy`, `draining` or `independent`; no two provider authorities run together. Shared quotas, backoffs, precise cursors and original hashes remain. Once core-only versions exist, blindly rolling back to a legacy reader is unsafe because it ignores component validity. Pause/drain ingestion while retaining the new permission-aware reader; use the runbook for recovery.

The implementation does not establish the specification's geographic latency, 1,000-user capacity, complete cover preparation or 24-hour canary acceptance by itself. Those measurements, relevant provider clarifications and display review remain public-release gates.
