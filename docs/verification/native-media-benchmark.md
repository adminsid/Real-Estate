# Cloud native image/video benchmark — 2026-11-15

Scope: one eligible retained OneKey listing photo and one generated video.
All transformations ran on Cloudflare. Docker Desktop built/pushed the deployment
image only. No inventory warmup, public release or paid media service was enabled.

## Measured results

| Job | Time including startup and stop | Original bytes | Saved output bytes |
| --- | ---: | ---: | ---: |
| One currently eligible listing photo | 7,751 ms | 57,825 | 143,334 across three profiles |
| Generated 3-second video | 9,424 ms | Generated in container | 176,158 across four files |

| Saved profile | Bytes | Verified format |
| --- | ---: | --- |
| Thumbnail | 7,016 | WebP |
| Card | 59,126 | WebP |
| Display | 77,192 | WebP |
| Video poster | 10,888 | WebP, 640×360 |
| MP4 preview | 79,215 | MP4 |
| HLS playlist | 139 | VOD, 3 seconds, relative authorized segment route |
| HLS segment | 85,916 | MPEG-TS, generated by FFmpeg |

The photo was already a small compressed 640×480 original. Fit-without-enlarging
preserved those dimensions for card/display; reencoding at the chosen quality
made these two files larger than the original. Thumbnail was useful; wholesale
reencoding is not justified by this sample. Future production selection must
retain efficient originals instead of assuming WebP always saves bytes. The card
was visually inspected and retained the source composition and OneKey watermark.

The video test exercised FFmpeg generation, decoding, poster creation, MP4
encoding and HLS muxing. The output was retrieved and its headers/playlist were
checked. Browser playback across Safari/Chrome/mobile has not been certified.

Both ledger rows were `ready`; a later status read reported `running:false`,
`paused:false`, and exactly two of four attempts used. Repeating the completed
photo POST returned HTTP 200 with `reused:true` without spending another attempt.
After the final deployment, repeating the video action also returned `reused:true`;
both jobs remained ready, attempt count stayed two, and the unauthenticated owner
page returned a Cloudflare Access redirect (HTTP 302).
All seven output objects were subsequently retrieved from R2 through the private
service after the container had stopped.

The initial long-running POST responses returned a connection-lost error even
though processing committed successfully. A regression fix reads the committed
ledger with a fresh Durable Object stub after connection loss; it never replays
the processing action. Covered by a dedicated test. No extra benchmark attempt
was spent solely to reproduce that transport interruption.

not billing measurements or account spending caps; platform startup/stop delays,
Workers/DO/R2/registry usage, unrelated services and tax are separate.
